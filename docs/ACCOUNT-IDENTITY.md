# 微信账号身份与别名

## 问题

同一个微信账号可能改过微信号，历史配置里因此出现多个 `account_id`，例如
`asdfhl` 和 `sadjf`。当前数据库把 `account_id` 当作所有消息、额度、游标和告警的
隔离键，所以两个别名会被当成两份账号，统计不会合并。

## 方案对比

### 方案 A：用户手动确认同一账号（安全、推荐作为兜底）

设置页列出所有账号，用户勾选“这些是同一账号”，确认后把别名绑定到一个主账号。
优点：不会误合并；缺点：需要用户操作一次。

### 方案 B：聊天记录相似度自动判断（只做建议）

比较联系人集合、消息时间分布、文本哈希重合度、共同群聊等，给出 0–100% 置信度。
**只提示，不自动合并**。两个不同账号可能有相同群聊，自动合并风险高。

### 方案 C：稳定 wxid 作为主身份（推荐）

微信 4.x 数据目录通常是：

```text
xwechat_files/<wxid>_<随机后缀>/db_storage
```

其中 `<wxid>` 比可见微信号稳定；可见微信号（alias）可以修改，但数据目录的 wxid
通常不变。把它作为 `stable_id`：

- 新采集统一落到稳定身份；
- 可见微信号、昵称、头像作为资料字段；
- 历史别名按“确认后合并”的方式迁移；
- 相似度只作为别名建议，不能替代用户确认。

## 本项目当前实现

- `wequota/account_profile.py` 只读本机 `wechat-cli` 已解密的 `contact.db`，
  推导 `stable_id`、微信号、昵称和头像 URL；
- `accounts` 表新增 `wechat_id / avatar_url / stable_id`；
- `/api/accounts` 返回资料，概览页显示头像、微信名、微信号和账号 ID；
- 身份弹层展示稳定身份，以及检测到的同身份别名；
- **合并必须用户确认**：`POST /api/accounts/merge` 只在 `confirm=true` 时执行。
  可以传 `stable_id` 自动识别同身份组，也可以传 `account_ids` 手动选择无法自动识别的
  旧别名；目标自动选择组内最新消息/最近同步/最近资料更新的账号；
- 迁移内容：消息（按 msg_id 去重）、额度规则、用量重建、告警、同步游标、per-peer
  游标、账号资料；别名写入 `account_aliases` 审计表；
- 合并后自动把 `collector.account_id` 更新为最新账号，避免后续采集继续写入旧别名；
- **不会自动调用相似度合并**；相似度只作为建议。

## 合并流程

1. 用户打开账号身份弹层；
2. 系统展示同 `stable_id` 的别名和最晚活跃账号；
3. 用户点击“合并到最新账号”并二次确认；
4. 后端事务迁移并写入别名记录；前端切到目标账号并重新加载数据；
5. 如果迁移失败，事务回滚；建议在合并前使用每日快照回滚点。
